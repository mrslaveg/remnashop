# Первичная миграция Remnawave v3 ID

Миграция переносит **только числовые ID Remnawave v3 в локальную БД Remnashop**. Пользователи, UUID, статусы, лимиты, подписки и настройки на панели Remnawave этим инструментом не изменяются.

## Что будет записано

Новая nullable-колонка subscriptions.remnawave_user_id BIGINT хранит числовой ID панели. Существующая subscriptions.user_remna_id остаётся без изменений. Заполняются только текущие подписки, на которые ссылается users.current_subscription_id; исторические подписки не переписываются.

## Предварительные условия

1. Сделать резервную копию базы Remnashop.
2. Остановить фоновые задачи и экземпляры бота на время первичной сверки/применения, чтобы другие процессы не меняли локальные подписки или панель параллельно.
3. Запустить команды из корня проекта в окружении Remnashop, где доступны его переменные окружения и зависимости.

Применить только DDL-миграцию локальной БД:

```bash
uv run alembic upgrade head
```

## Шаг 1 — dry-run

```bash
uv run python -m scripts.remnawave_v3_migrate \
  --report-file /tmp/remnawave-v3-migration-report.json
```

Это режим по умолчанию. Скрипт:
- читает метаданные и список пользователей панели;
- читает только текущие локальные подписки;
- ищет соответствия по точной ссылке подписки / short UUID, Telegram ID и ожидаемому имени rs_<telegram_id> (для web-пользователей — rs_web_<local_id>);
- использует VLESS UUID только как дополнительный сигнал, но никогда как единственное основание;
- выявляет неоднозначные совпадения, конфликты, дубли и уже заполненные ID;
- сохраняет JSON-отчёт без токенов ссылок подписки.

Если хотя бы одна текущая подписка не сопоставлена однозначно, применение будет заблокировано целиком.

## Шаг 2 — применение только в локальную БД

Только после проверки отчёта и резервной копии:

```bash
uv run python -m scripts.remnawave_v3_migrate \
  --apply \
  --confirm REMNAWAVE_V3_LOCAL_DB_ONLY \
  --report-file /tmp/remnawave-v3-migration-report.json
```

Вся запись выполняется одной транзакцией PostgreSQL. Перед записью скрипт блокирует и повторно сверяет локальные строки с исходным снимком. При расхождении или ошибке транзакция откатывается. Повторный запуск не перезаписывает уже совпадающие ID.

## Гарантия read-only для панели

HTTP-клиент скрипта имеет request hook, который разрешает только GET. Любая попытка выполнить POST, PUT, PATCH, DELETE или другой метод будет отклонена до отправки запроса. В самом сценарии нет вызовов создания, обновления, отключения, удаления пользователей, сброса трафика или HWID.

Параметр panel_write_requests_allowed в отчёте всегда равен false. Пользователи панели не меняются этим инструментом.
