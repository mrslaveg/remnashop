# Первичная миграция Remnawave v3 ID

Миграция переносит **только числовые ID Remnawave в локальную БД Remnashop**. Пользователи, UUID, статусы, лимиты, подписки, трафик, HWID и настройки на панели Remnawave этим инструментом не изменяются.

В БД используется отдельная nullable-колонка `subscriptions.remnawave_user_id BIGINT`. Существующая `subscriptions.user_remna_id UUID` остаётся неизменной и сохраняет историческую идентичность.

## Административная миграция из Telegram

В ветке `feat/remnawave-v3` доступен экран миграции в админке рядом с «Импортом пользователей». Команда для прямого открытия: `/remnawave_migration`. Доступ есть у ролей с разрешением `VIEW_IMPORTER` (OWNER/DEV).

Экран выполняет dry-run, показывает статистику и конфликты, а применение требует отдельного подтверждения. Полные JSON-отчёты и логи сохраняются в `logs/remnawave-v3-migration/` (том `./logs` в Docker Compose).

При запуске с Remnawave 2.7.x/2.8.x бот работает в ограниченном режиме: обычные пользовательские действия блокируются, а разрешённым администраторам доступны только экран миграции и команда `/remnawave_migration`. На старой API-линии экран сопоставляет пользователей по точному legacy UUID. После успешного применения ограничение сохраняется до обновления панели до 3.x и перезапуска Remnashop. В этом режиме Telegram пропускает только экран миграции, а публичные HTTP API и платежные маршруты отвечают 503. На время процедуры также останови Taskiq worker и scheduler, чтобы фоновые задачи не запускали операции с подписками.

Если панель уже обновлена до Remnawave 3.x, но локальные числовые ID ещё не заполнены, действует тот же ограниченный режим; экран использует v3 users stream и проверяет соответствия по доступным идентификаторам.

**Для панели 2.8.0 можно использовать сам экран админки** — запуск ограниченного режима специально разрешает этот сценарий. CLI-сценарий ниже остаётся резервным вариантом для контролируемого запуска вне Telegram.

## Рекомендуемый сценарий для перехода с Remnawave 2.8.0

**Откатывать панель на 2.7.4 не требуется.** Мигратор поддерживает старую API-линию Remnawave 2.7.x и 2.8.x: для каждой текущей локальной подписки он читает пользователя через точный старый UUID. Текущая связка Remnashop + Remnawave 2.8.0 может оставаться рабочей до планового окна миграции.

### 0. Подготовка

1. Пока текущая связка Remnashop + Remnawave 2.8.0 работает, подготовить резервные копии PostgreSQL Remnashop и Remnawave, а также версионированный образ Remnashop с этой ветки.
2. В согласованное окно остановить Taskiq worker и scheduler. Основной сервис Remnashop оставить запущенным: через него администратор откроет экран миграции. На время процедуры публичные HTTP API и платежные маршруты будут автоматически отвечать 503.
3. **Оставить Remnawave на 2.8.0** на время локальной миграции ID. Не откатывать панель и не обновлять её до завершения этапа 3.

### 1. Добавить колонку в локальную БД

Из корня проекта и с теми же переменными подключения к PostgreSQL Remnashop:

```bash
uv run alembic upgrade head
```

Это локальная DDL-миграция: добавляется только nullable `BIGINT` и индекс. Существующие строки и данные Remnawave не переписываются.

### 2. Сопоставить UUID с числовыми ID на старой панели

В запущенном боте открыть Dashboard → **«Миграция Remnawave v3»** рядом с кнопкой импорта пользователей. Альтернативно отправить команду `/remnawave_migration`.

Нажать **«Проверить соответствия»**. Для панели Remnawave 2.7.x/2.8.x мигратор:
- читает `GET /api/system/metadata`;
- для каждой текущей локальной подписки делает только `GET /api/users/{старый_UUID}`;
- проверяет, что UUID в ответе панели в точности совпадает с запрошенным UUID;
- извлекает числовой `id`; при наличии Telegram ID сверяет его с локальным пользователем;
- не использует username, short UUID или URL как fallback для v2-сопоставления;
- блокирует применение при отсутствующем пользователе, конфликте, неоднозначности или повторном назначении одного panel ID нескольким локальным подпискам.

В отчёте поле `panel_api_line` будет равно `v2_legacy_uuid_lookup`. Успешное сопоставление по точному старому UUID — основное доказательство идентичности; совпадающий Telegram ID дополнительно усиливает проверку.

Проверь отчёт. Все текущие подписки должны иметь статус `matched` или `already_migrated`. Любой `unmatched`, `conflict`, `duplicate_local_mapping` или `existing_id_conflict` блокирует применение целиком.

Если экран показывает только `matched` и `already_migrated`, нажать **«Перейти к применению»**, проверить предупреждение о резервной копии и подтвердить **«Применить только в БД бота»**.

Применение выполняется одной транзакцией. Перед записью скрипт повторно читает идентичности панели и сверяет снимок, затем блокирует таблицы текущих подписок и пользователей на время проверки и записи. При расхождении транзакция отменяется. Заполняется только `subscriptions.remnawave_user_id`; `user_remna_id` и все остальные поля не меняются.

Полный JSON-отчёт и лог сохраняются в `logs/remnawave-v3-migration/`. На экране показываются итоговые счётчики, первые пять проблемных записей и хвост лога.

CLI остаётся резервным способом запуска вне Telegram; его команды приведены ниже в разделе аварийного восстановления.

### 3. Проверить результат и обновить панель

Перед обновлением Remnawave убедиться, что:
- экран сообщил об успешном применении;
- в JSON-отчёте нет нерешённых статусов;
- количество успешно сопоставленных текущих подписок равно числу текущих локальных подписок;
- `panel_write_requests_allowed` равно `false`;
- в PostgreSQL заполнен `remnawave_user_id` для всех текущих подписок.

Сохранить отчёт вместе с резервной копией. Только после этого обновлять Remnawave до поддерживаемой версии 3.x.

### 4. Обновить панель и проверить v3

После успешного применения локальных ID обновить Remnawave до поддерживаемой версии 3.x и перезапустить Remnashop. До этого момента бот останется в ограниченном режиме. При запуске на v3 приложение проверит заполнение всех текущих ID; если остались пропуски, оно продолжит работать только в режиме миграции.

После запуска открыть экран миграции ещё раз и выполнить dry-run. Для Remnawave 3.x инструмент читает полный поток пользователей и проверяет, что каждый сохранённый числовой ID присутствует в панели. Если в обоих источниках есть Telegram ID, они также должны совпадать. Для корректных строк отчёт показывает `already_migrated`; отсутствующий ID или конфликт Telegram ID блокирует проверку.

Повторно сопоставлять такую строку по username/URL не нужно: исходная связь уже была установлена точным UUID-запросом на v2. Любое расхождение требует ручного разбора — не удалять и не пересоздавать пользователя на панели.

Если проверка прошла, ограничение будет снято после перезапуска Remnashop на панели 3.x с заполненными ID. Рабочий адаптер использует числовые panel ID, а старый UUID остаётся в историческом поле.

## Гарантии и ограничения

- При Remnawave 2.7.x/2.8.x, при незаполненных ID на v3 или если версию панели не удалось проверить, приложение запускается в ограниченном режиме. Telegram middleware разрешает только миграционный экран для OWNER/DEV; публичные HTTP API и платежи отвечают 503. На v3 с полностью заполненными ID ограничение снимается после перезапуска.
- Ограничение не останавливает Taskiq worker/scheduler автоматически: их нужно остановить на время миграции. Если панель недоступна, приложение включает ограниченный режим и не разрешает обычные пользовательские операции.
- Мигратор не содержит вызовов создания, изменения, включения/отключения, удаления пользователей, сброса трафика, отзыва подписок или управления HWID на панели.
- HTTP event hook блокирует любой запрос, кроме GET метаданных, GET v3 user stream и GET по UUID-формату старого v2 user endpoint. Любой POST/PUT/PATCH/DELETE запрещён до отправки.
- В v2-режиме инструмент запрашивает только UUID, полученные из текущих локальных подписок, а не перебирает/изменяет пользователей панели.
- В локальной БД записывается только числовой ID в новую колонку. Исторический UUID не перекодируется и не затирается.
- Исторические, не текущие подписки не мигрируются этим сценарием; они не используются текущим рабочим потоком. Их старые UUID остаются в БД.
- Не запускать миграцию параллельно с работающими экземплярами Remnashop и не обновлять панель между dry-run и apply.

## Аварийный запуск CLI вместо Telegram

Если админский экран недоступен, остановить worker/scheduler и выполнить мигратор вручную из контейнера/окружения с теми же переменными Remnashop.

Для Remnawave 2.7.x/2.8.x сначала выполнить dry-run, проверить JSON-отчёт, затем применить:

```bash
python scripts/remnawave_v3_migrate.py --report-file /tmp/remnawave-v3-migration-report.json
python scripts/remnawave_v3_migrate.py --apply --confirm REMNAWAVE_V3_LOCAL_DB_ONLY --report-file /tmp/remnawave-v3-migration-report.json
```

Для Remnawave 3.x dry-run после обновления панели:

```bash
python scripts/remnawave_v3_migrate.py --report-file /tmp/remnawave-v3-migration-v3-report.json
```
